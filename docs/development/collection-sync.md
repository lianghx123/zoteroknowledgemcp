# Continuous Collection Synchronization

Choose **Sync Settings…** from a native Zotero collection's context menu, select a knowledge destination and choose a synchronization mode. The same dialog opens from the mapped destination root folder to edit their existing relationship. The source collection and descendants are mirrored as knowledge folders below that location. Source item additions create metadata memberships and admit eligible local PDF attachments to the existing durable parser. Source folder renames and moves within the selected subtree update their mapped knowledge folders. One-time collection admission remains available separately.

Only each explicitly linked source root and its mapped destination root receive a sync overlay and a Sync Settings entry. Descendants continue synchronizing through that relationship without their own badges or settings entry; newly added source descendants follow the same rule before their first scan. Its tooltip and context menu show the destination path. Import Tasks presents a persistent sync folder with pause/resume controls and last-scan changes. Pausing retains the binding and memberships. Stopping synchronization in the settings dialog converts its retained placements to manual origins and removes the live link from the UI. Clearing sync history hides only finished child records and the empty task container; active and future jobs remain visible, including after restart. The binding continues synchronizing. Legacy binding-wide hidden markers migrate once to per-record history, without hiding active work.

The overlay uses two compact horizontal SVG harpoons, each with only one half of the arrowhead and a three-unit shaft separation in the 12-unit view box. Its background stays transparent in every state. The normal strokes use the theme's accent color; focused selection uses white strokes, and inactive selection follows the row text color. It retains the native folder icon and destination tooltip.

Failed or partial child parsing now makes an enabled sync task show attention. Its Retry action retries the failed child jobs explicitly after reconciliation; ambiguous submissions are excluded and still require recovery by remote ID. Paused links remain Paused even if their children have failures. Reusing a visible, previously ungrouped manual task associates it with the sync folder without submitting it again. Cleared history stays hidden and jobs already in another batch retain their grouping.

## Modes and Native Settings

| Mode | Chinese name | Source additions | Source removals | Knowledge-side edits |
| --- | --- | --- | --- | --- |
| `mirror` | 镜像同步 | Import | Remove binding-owned placements | Membership and mapped hierarchy are read-only |
| `flexible` | 柔性同步 | Import | Remove binding-owned placements | Independent additions and removals |
| `append` | 追加同步 | Import | Retain imported placements | Independent additions and removals |

Existing bindings migrate to `flexible`. Local removals in flexible/append mode persist exclusions keyed by binding, destination node and native item key; folder exclusions use the native collection key independently of the local folder lifetime. Restoring an item/folder or explicitly re-adding an item clears the corresponding exclusion. The dialog can clear all exclusions, pause/resume, change mode or stop the relationship while retaining items. Changing to mirror clears exclusions. Existing destinations are shown read-only in this dialog; stop and create a new relationship to select a different parent. Multiple selected source collections can create relationships together; existing relationships are edited individually in the relationship selector.

Restrictions are checked in repository transactions for admissions, item removal, ancestor/library deletion and folder creation, including actions initiated by drag and drop. Metadata refresh and parsing remain available. Other knowledge locations and unrelated manual origins stay independent. Empty mapped folders are retained after source removal to protect manual/shared folder data. The plugin never writes changes back to source collections or Zotero items.

## Persistence and Ownership

`zotero_bindings` stores source library identity, collection key, destination and enabled state. `zotero_collection_links` maps native collection keys to knowledge node IDs. `membership_origins` records each binding-owned placement independently of manual or other binding origins. `plugin_state` retains small per-binding display/error/history state. Migrations 0007–0008 extend the existing binding with `sync_mode`, add stable-key item/folder exclusions and reserve a transactional resource purge scope plus a durable file cleanup queue. Zotero's database schema is unchanged.

Reconciliation uses native collection and item APIs. It runs after startup, debounced collection/item/group notifications and a 30-second fallback interval. Scans are serialized. Removing an item from a source collection deactivates only the relevant binding origin; placement/library membership is removed only when no other live origins require it. Original Zotero items, PDFs and published content are retained. Known removed source collections prune their binding origins and disable tracking; unavailable libraries or incomplete native member/tree scans preserve memberships and show attention instead of treating an unavailable source as empty. PDF preparation errors (including missing and oversized attachments) are handled separately: they show attention but do not stop descendant traversal or pruning after a complete native membership scan. Metadata memberships and other eligible PDFs are still admitted.

Each scan validates the native library identity and destination. Locally removed flexible/append folders are skipped using collection-key exclusions. Explicitly clearing exclusions creates a fresh mapped folder without consuming the old Trash operation. A removed parent destination requires stopping and relinking. Already accepted parse jobs keep their remote identity. Repeated scans reuse unchanged terminal failures/partial results until an explicit retry and do not repeatedly submit the same failed PDF. Changed PDF fingerprints can create new work. Metadata-only edits preserve the parser's input fingerprint behavior.

Folder mappings reuse matching destination folders so manual content can coexist. Empty mapped folders are retained after source removal; this avoids deleting shared/manual folders or their knowledge data. Only source-derived membership origins are pruned. Synchronization is one-way: changes in the knowledge tree are not written back into Zotero. Sources must remain available locally; missing PDFs are not automatically downloaded.

## Lifecycle and Verification

Admission rechecks the binding's enabled state, destination ancestry and item/folder exclusions in the same transaction as membership creation and Trash readmission. A local deletion that wins that transaction leaves its recovery entry intact; the scan skips the excluded member. Purging a chosen parent destination disables and invalidates the old binding using a separate `plugin_state` key (`collection-sync-invalid-target:<id>`). Lists and binding reuse exclude invalid relationships, and configure/resume reject them. The retained nullable foreign key does not mean a new library-root destination; the user must explicitly choose a destination to create a new relationship. Retained provenance can continue referencing the disabled record until its owners are purged.

Folder creation, replacement, rename/move and mapping writes also recheck local exclusions and the complete destination ancestry in one transaction. A deletion between the scan's initial check and folder mapping cannot recreate an empty same-name folder or block Trash restoration. Failed mapping writes roll back the new folder, library version and outbox event together. Pruning validates the chosen destination again, including in append mode; a removed parent shows attention until restored or explicitly replaced by a new relationship.

The application owns one `CollectionSyncService`, closes its observer/timers and drains accepted scans before shutting down the parsing service or database. `ImportTasksService` combines synchronization and parse snapshots, while each window owns its badge adapter and task view. Preference panes register through Zotero's native `PreferencePanes` API and the task settings action uses `Zotero.Utilities.Internal.openPreferences`.

Synthetic Node tests cover recursive/empty folders, rename, incremental admission, source unavailability/removal, manual-origin preservation, pause/restart, unlink retention, failure deduplication and hidden history. Task UI tests cover multiple selection/context actions, combined progress and column preference migration. Settings tests cover validation, conflicting edits, generation retention on history deletion and native navigation routing.

Displayed knowledge folder hierarchies use Zotero-style ` › ` separators consistently in settings, tooltips, context menus, task locations and item details. Historical preformatted task/Trash locations are adapted when displayed without rewriting their records.

Audit regression coverage includes unavailable/oversized PDF preparation while traversing a new child and removing a stale source member, incomplete native scans that must not prune, clearing finished history with active and later jobs, restart behavior and one-time migration of legacy hidden relationships. Source data remains read-only and no embedding work is introduced.
