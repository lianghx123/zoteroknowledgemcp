# Knowledge Membership and Metadata Admission

The knowledge service admits native literature metadata and attachment identities into independent plugin libraries and folders. Parsing, content publication, embeddings and MCP are separate services sharing these mappings; see [project status](project-status.md).

After successful metadata admission, the UI can queue eligible PDFs through the [parsing service](parsing.md) when enabled. Parsing owns file fingerprints, generations, artifacts and publication. The metadata repository does not dispatch workers or treat metadata presence as extracted content.

## Confirmed Metadata Projection

Zotero remains authoritative. Store a bounded, versioned bibliographic projection, source links, and knowledge organization in the existing plugin database. Do not copy the native database or persist an unrestricted item export.

| Information | Storage and behavior |
| --- | --- |
| Title | `knowledge_resources.title`, preserving the original text. A blank title receives a display fallback; a nonblank value exceeding the existing 1,000-character schema limit is rejected with an actionable per-item error rather than silently truncated. |
| Type, language, publication date, abstract | `resource_type` retains native item type; `language`, `publication_date`, and `abstract` preserve their native textual values. Do not infer dates or generate summaries. |
| Creators | `contributors_json`: ordered creator records with native creator role, first/last name or single-field organization name. No guessed affiliation or identifiers. |
| Promoted bibliographic fields | Native `publicationTitle`, `volume`, `issue` and `DOI` map to nullable `knowledge_resources.publication_title`, `.volume`, `.issue` and `.doi` columns. These four keys are excluded from `metadata_json.fields`. Values retain their original textual form; cleared fields become NULL. |
| Other bibliographic fields | `metadata_json.fields`: populated native fields valid for the item's type, including book/conference title where stored under another native field name, publisher, institution/university, pages, edition, series, place, short title, URL, access date, archive/catalog/call-number fields, rights, Extra and ISBN/ISSN. Exclude attachment file paths, note bodies, annotations, relations, and complete raw item exports. |
| Identifiers | `resource_identifiers`: native DOI, ISBN, and ISSN values, with conservative deterministic normalization and original values retained. Other identifiers remain in available bibliographic fields/Extra; parsing Extra into inferred arXiv/PMID/PMCID identifiers is deferred. |
| Tags | `metadata_json.tags`: tag name and native tag type. Tags remain source metadata and do not create knowledge folders. |
| Native source identity | `zotero_libraries` and `zotero_item_links`: stable plugin library UUID plus native item key, native library identity/permission projections, local numeric ID as a lookup hint, native modified/version hints, visibility state, and metadata fingerprint. |
| Attachment metadata | `resource_sources` plus attachment `zotero_item_links`: native attachment key and parent key, title, MIME type, native link mode, and availability. Include child attachments without copying bytes, full text, file hashes, or private local paths into public metadata. |
| Knowledge organization | Library membership, optional folder placements, and manual provenance. Membership does not claim that content has been processed. |
| Plugin bookkeeping | UUIDs, UTC timestamps, record/metadata versions, deterministic metadata fingerprint, mutation receipt, revision, and durable outbox event. |

Source availability starts unknown/pending unless checked through a native availability API. Do not claim that a file is present solely because an attachment record exists. Metadata admission leaves the canonical source unset. The first successful parse publication sets it if still unset; later publications do not silently replace an existing selection or concatenate attachments.

Native item metadata changes refresh the stored projection and displayed state. Native trash/unavailability hides the item from active knowledge views as appropriate without removing the original or immediately destroying recoverable plugin records. Startup reconciliation repairs missed notifications for already admitted resources; it does not admit unselected native items.

## Metadata and Membership Tables

Metadata admission uses the tables below. Migration 0005 adds/backfills four bibliographic resource columns and removes their former JSON keys. Migration 0006 adds six dedicated Trash entry/recovery-link tables and imports legacy `plugin_state` recovery JSON. Migrations 0001-0005 remain unchanged. The compatible 0006 import was optimized with identical DDL/recovery semantics; its explicitly accepted compatible checksums remain supported without rewriting already-upgraded history. The validated pre-upgrade snapshot is retained.

| Table | Use |
| --- | --- |
| `knowledge_libraries` | Default and user-created knowledge libraries. |
| `knowledge_resources` | One logical resource per admitted native anchor item. |
| `zotero_libraries` | Native source-library identity and permission/availability projection. |
| `zotero_item_links` | Unique native item/attachment mapping and local lookup hints. |
| `library_resources` | Resource membership in a knowledge library; repeated admission reuses/reactivates it. |
| `membership_origins` | Manual library/folder membership provenance, independent of collection-binding origins. |
| `resource_identifiers` | Populated DOI/ISBN/ISSN values only. |
| `resource_sources` | Attachment identities and metadata only; no parsed content generation. |
| `library_nodes` | User-created ordinary knowledge folders. |
| `library_items` | Optional folder placements; adding to a library root creates no fake folder. |
| `resource_revisions` | Append-only resource creation and metadata/source/lifecycle changes. |
| `mutation_receipts` | Replay of accepted UI operations; repeated clicks still deduplicate by native identity/membership. |
| `change_outbox` | Durable change facts committed with the mutation; local full-text/vector maintenance observes the event sequence. Cloud synchronization is unavailable. |
| `plugin_state` | Installation identity used to bind UI operation authority and native-library mappings, plus migration checksums; Trash recovery data no longer belongs here. |
| `knowledge_trash_entries` | One recovery operation: stable ID, item/folder/library kind, original name, library/folder target, display-location snapshot and deletion time. |
| `knowledge_trash_resources` | Ordered resource references and a checked flag for resources deleted with an exclusive-library deletion. |
| `knowledge_trash_folders` | Ordered, library-scoped folder identities owned by the recovery operation. |
| `knowledge_trash_relations` | Ordered, library-scoped knowledge-library membership identities to restore. |
| `knowledge_trash_placements` | Ordered, library-scoped folder-placement identities to restore. |
| `knowledge_trash_origins` | Ordered, library-scoped membership-provenance identities to restore. |

Metadata repositories own admission and membership. Separate services own [collection synchronization](collection-sync.md), [parsing](parsing.md), [vector retrieval](vector-retrieval.md) and [local MCP access](mcp.md). The one-time collection action admits direct items without creating a continuous binding. HTTPS and relay adapters remain unavailable.

Knowledge Base Information displays the parser and model beneath each attachment that has published parsed content. This provenance follows the attachment's active generation through its parse run and immutable provider configuration, not the currently selected parser or most recent failed attempt. Multiple attachments can show different parsers; clearing task history preserves the display. Unparsed attachments and generations without parser provenance omit the parser line. Only provider/model labels enter the UI snapshot; endpoints, credentials and provider options remain private.

## Admission Rules

- Branding: `addon/content/ui/knowledge.svg` is the original Book K mark drawn for this project from open-page curves and a K letterform, without third-party icon paths. Top-level plugin item/collection context commands use Zotero MenuManager's native `icon` property; nested destination names keep their ordinary presentation. Knowledge navigation, information sections and addon metadata reference the same SVG. Context color supports native menu hover and theme colors.
- Default target: the default knowledge library root. A hierarchical target submenu allows another library or ordinary folder.
- Both **Add to Knowledge Base** item-menu entries are limited to native Zotero literature views. Knowledge overview, library, folder, combined and Trash views hide them; copying to other knowledge locations remains available by dragging.
- Accept regular bibliographic items and standalone attachments. Selecting a child attachment admits its parent bibliographic item and links the parent's attachments. Standalone notes and annotations are not admitted as independent literature resources.
- Repeat addition to the same target is idempotent. The same native item can have multiple library/folder memberships while retaining one resource identity.
- Store bibliographic metadata and attachment identities on admission; do not copy PDFs, Markdown, notes, annotations, or parsed text. Notes remain visible in native Zotero UI.
- Bibliographic changes follow Zotero one way. Plugin organization changes and membership removal never modify native bibliographic fields, collections, or original attachments.
- Removal distinguishes current folder from current knowledge library. Preserve resources required by other memberships and keep original Zotero items untouched.
- Each accepted item operation is transactional and versioned. Batch operations return per-item outcomes; invalid items do not silently prevent unrelated valid items from being admitted.
- Added items without published content display "Added — not processed". Published content changes the title marker and details to parsed or partially parsed; missing/unavailable native sources add a warning. No simulated parsing status appears in the shipped UI.

## Metadata Updates and Ownership

Publication title, volume, issue and raw DOI now update/clear in dedicated resource columns. DOI normalization and identifier ownership still use `resource_identifiers`; extracting these columns does not remove that table. Migration 0005 changes storage format (`metadata_schema_version = 2`) without creating logical metadata revisions or changing existing fingerprints. Subsequent real native changes retain the ordinary version/revision rules below.

`zotero_libraries` describes original personal/group source libraries, while `knowledge_libraries` describes plugin organization. A source-library UUID plus `zotero_item_links.item_key` identifies the original item; numeric native IDs only help local lookup. This source mapping supports deduplication, source navigation, identity/permission checks and one-way metadata refresh of admitted resources. It neither admits every source-library item nor mirrors collection folders. Collection synchronization and MCP access grants are separate records/features.

Zotero owns bibliographic fields, creators, tags, identifiers and attachment associations. Changes flow from Zotero into the knowledge database. The plugin does not write these values back to Zotero. Plugin summaries, unrelated plugin metadata and knowledge folder placements are preserved when the native projection is refreshed. Clearing a Zotero field clears its saved projection; removing a native identifier removes the Zotero-owned identifier row. Other authorities' identifier rows remain intact.

The service observes native `item`, `item-tag`, `tag` and `group` notifications and coalesces changes for 150 ms. It refreshes only already admitted resources. Startup reconciles all active memberships to recover changes made while the addon was disabled. The right pane and knowledge collection menu also provide manual refresh. No background scan automatically admits the rest of a Zotero library.

A deterministic fingerprint distinguishes bibliographic changes from attachment/lifecycle changes. Unchanged refreshes do not create new resource versions or receipts. Bibliographic changes advance `metadata_version`; metadata, source and membership changes advance the overall resource `version` and append a revision/outbox event in the same transaction. Attachment-only changes do not advance the bibliographic metadata version. Local embedding and vector maintenance observe the outbox sequence to detect committed changes. Parsing admission, collection reconciliation and MCP requests retain their own service boundaries; no cloud-sync consumer is enabled.

Writes are serialized and transactional. If projection validation or persistence fails, the last valid metadata and memberships remain available, with an in-memory refresh warning and a manual retry action. Warnings are reconstructed on startup reconciliation rather than persisted as a processing status. Missing native items are marked deleted; inaccessible libraries/items are marked unavailable; trash and restore retain identity. A changed external library identity is marked unavailable without adopting the replacement's metadata. Startup and explicit refresh can recover availability.

Removing a folder placement preserves other placements. Removing from a knowledge library removes its manual root/folder memberships. Neither operation deletes the Zotero item, attachment file or resource history; readmission reuses the same native resource identity. Resources with no active knowledge-library membership are excluded from automatic reconciliation until readmitted.

### Zotero Account and Data-Directory Lifecycle

The plugin has no login or account system. `external_library_id` records Zotero's optional numeric user ID or group ID as a source-identity check; it is not a plugin authentication credential. First-time linking of an existing local library to a Zotero account can populate a previously absent user ID without replacing that library.

In installed Zotero 10.0.6, ordinary logout (`preferences_account.js`, `unlinkAccount` without removing local data) removes the API key but retains the local library and `Zotero.Users.getCurrentUserID()`. It does not produce a user ID transition from A to null. Removing local data or confirming an account switch writes `reset-data-directory` and restarts. Startup (`xpcom/zotero.js`, `_initFull`) clears data-directory entries other than `pipes`, recreates the native database, and only later starts plugins. `syncLocal.js`, `checkUser` also requires a reset before an existing database can sync with a different account. See Zotero's [account-switching documentation](https://www.zotero.org/support/kb/switching_accounts).

Because plugin storage is inside that data directory, this reset also removes `knowledgemcp/knowledge.sqlite`, knowledge memberships/metadata and the pre-upgrade snapshots alongside it. The subsequent plugin startup initializes a fresh empty knowledge database. A sibling database is isolated from Zotero's SQL schema but does not survive a directory reset. Ordinary logout, addon reload and addon uninstall do not invoke that reset or delete plugin storage.

Consequently, a synthetic A-to-null-to-B projection with the old plugin database retained is not evidence of a normal native account-switching defect. No account migration or automatic knowledge reassociation is added for this path. Manual database replacement, selective backup restoration and plugin data copied across profiles are separate recovery scenarios; their source-identity/reassociation policy remains future work. Retaining knowledge across a native account reset would require a separately designed export/backup outside the reset directory. This assessment uses installed source inspection and the official documentation, not a destructive account-switch test.

Deleting a knowledge library is a separate context-menu action with a native confirmation dialog. Its checkbox, unchecked by default, optionally marks resources used only by that library as deleted. Without it, metadata stays available for readmission. In either case the library, its complete folder tree and its memberships are logically deleted in one transaction, and resources shared with another nondeleted knowledge library are preserved. Deletion retains tombstones and revision history; it is not a permanent physical erasure of SQLite records. Explicit readmission recovers the same resource UUID. Zotero items and attachments are untouched.

If the deleted library was the default, an existing active library becomes the default. Deleting the last library leaves no active knowledge libraries after restart; Trash remains available. The first subsequently created library becomes the default. Initial setup creates one empty default library without sample items, sample folders or an Unfiled entry.

Deleting a knowledge folder removes its complete subtree and those folder placements in one transaction. It keeps all resources in the same knowledge library. When a resource had no other placement/root origin there, deletion creates a root membership so it remains visible when selecting the library. Other folder/library memberships, metadata, Zotero items and files are preserved. The library/resource versions and revision/outbox facts advance with the deletion. The context menu provides a native confirmation with Cancel as the default action.

## Knowledge Trash and Tree Persistence

The knowledge overview has its own **Trash** after the active libraries, using Zotero's empty/full trash icons. Each item-membership removal, folder-subtree deletion or library deletion writes a `knowledge_trash_entries` row and foreign-keyed resource/folder/relation/placement/origin references in the same transaction as the tombstones. These are plugin-owned business tables, separate from Zotero's database. Migration 0006 imports existing `knowledge-trash:<UUID>` JSON from `plugin_state`, preserves entry IDs, times, original targets and ordered references, and removes those legacy keys only after a successful import. Duplicate IDs in old arrays are normalized to one reference. Invalid records or missing/cross-library references roll back the upgrade; the old records and pre-upgrade snapshot are retained. Existing tombstones from versions without recovery records are not inferred into new deletion operations.

All array-based Trash predicates and mutations, including capture, restore, overlap purge and folder-subtree deletion, share `database/batches.ts`: at most 200 IDs per predicate or 200 four-column recovery rows per insert. Fixed scope/SET bindings are included in a test-enforced 999-parameter ceiling. References are deduplicated before query/insert batching; rewritten recovery lists retain their original relative order and continuous positions. All batches use the caller's transaction, so any later-batch failure rolls back earlier model/recovery/audit writes. Readmission checks join the persisted origin references, avoiding an accumulated ID predicate. Folder recovery caches parent availability and checks sibling conflicts against one active-folder map, including folders falling back to root. The schema remains unchanged; these fixes do not establish unlimited memory, latency or UI-scale guarantees.

The compatible 0006 legacy importer materializes only scalar entry/library/reference IDs and positions before grouping, then applies resource deletion flags through a relational subquery. Sorting no longer repeats the complete JSON document per reference. Duplicate references retain their first source position, invalid input still rejects the transaction, and legacy cleanup remains last. See [scale audit and verification](trash-scale-verification.md) for the complete operation matrix and compatibility policy.

Trash metadata snapshots use an indexed `EXISTS` query against `knowledge_trash_resources`, rather than binding the accumulated resource IDs into a single `IN` query. The number of SQL parameters therefore stays independent of the total Trash resource count. Multiple recovery locations for one resource return its anchor only once; resources without a Zotero mapping remain in the recovery records, and active resources without a Trash reference stay outside the Trash metadata list. This also protects refresh and startup after many independent deletion operations. The read-path change requires no schema migration.

Native item-list scoping uses `ui/knowledge/search-scope.ts`: one official native temporary table per library scope, created with the `id` column expected by Zotero's `tempTable` condition. This replaces per-item OR predicates that exceed native SQLite's expression-depth limit at large item counts. The entire scope is retained for native quicksearch, tags and advanced filters; unexpected results are still intersected with the allowed IDs. The owned table is dropped from the `temp` namespace in `finally`, including query failure and disposal during an in-flight request. Result tables returned to native views continue using the API's default `itemID` column and native caller ownership.

Trash is a single leaf in the left tree. Its middle list mixes individually removed native literature and deleted folder/library rows, following Zotero's native collection/item Trash design. Empty folders and missing-source item placeholders remain visible there. Select one or more rows and choose **Restore to Original Location** in the item context menu or click the native-style restore button above the right pane. The selected-row native restore command is routed to the same knowledge operation. **Restore All Knowledge Trash** in the left-tree context menu restores all operations. Restoring a folder/library recovers its entire recorded subtree. A folder's retained library items are not separately listed as deleted literature merely because that folder was removed.

`ui/knowledge/trash-list.ts` adapts the native mixed-object row provider. Folder/library/placeholder rows use transient, unsaved `Zotero.Collection` display references with plugin-owned string identities; save/erase methods reject. These references never enter the native collection database or notifier. Ordinary removed documents retain their original native item references. Name quicksearch filters folder rows; advanced item conditions and tags hide them like native Trash. Native filtering requires item-query safe defaults because these references enter before Zotero normally appends its own trashed collections. Selected-object access includes folder rows, while selected-item access continues to include only actual Zotero items. Reversible adapters route restore, block native activation of Trash rows and release the row-provider/right-pane hooks on unload.

Restore reactivates the recorded identities and original folder memberships. A separately deleted parent folder or library is restored first through its own recovery entry. Folder-deletion fallback root memberships are retained. Library restoration preserves the current default library; when none exists, the restored library becomes default. Each affected resource/library advances its version and records a revision/outbox event. Recovery entries are removed only after a successful transaction; a duplicate restore is harmless. A conflicting library name or sibling folder name cancels the complete restore batch with a readable message. Remove the conflicting location before retrying; current records are never replaced. Readmission consumes an item recovery entry only when every recorded original membership origin is active again; readding only at the library root or one folder leaves missing placements recoverable.

Source reconciliation includes resources present only in knowledge Trash. Restoring knowledge membership never restores or edits an item in Zotero's native Trash. Missing native originals use recoverable placeholder rows in the middle list. Knowledge Trash rejects incoming admission drops and routes native selected-delete/empty-trash commands to its own confirmed knowledge operations; it does not claim to be Zotero's native Trash.

**Move to Knowledge Trash** is available in the item context menu for the overview, single knowledge libraries/folders and combined knowledge selections. It removes selected resource memberships from the selected knowledge libraries, including all their folder placements, in one transaction. Other libraries remain unchanged. The overview targets all active knowledge libraries. **Remove from This Knowledge Folder** remains a distinct, single-folder placement action. Both record recoverable membership removals.

The Trash item menu and right-pane header offer **Delete Permanently…** for selected literature and folder/library display rows; **Empty Knowledge Trash…** in the left-tree menu applies to all recovery entries. The native confirmation defaults to Cancel and explains that deletion cannot be undone and Zotero originals remain intact. Selected deleted folders include their separately deleted descendant folders. Selected deleted libraries include all their remaining recovery entries. Independent item entries whose folder is permanently discarded can still be restored at the library root. A successful restore reactivates a shared resource even if another deleted library had marked its resource record deleted.

Permanent deletion removes recovery rights and unreferenced ownership rows transactionally. Overlapping recovery operations in the same knowledge library cannot later resurrect the discarded membership; independent active memberships and recovery rights in other knowledge libraries remain valid. Without active ownership, surviving recovery rights or incoming literature references, the resource and its sources, native mappings, parse history, published generations, revisions, search rows and managed artifacts are physically deleted. Reimport then creates a fresh resource and requires parsing again. Shared stored files survive until their last owner is deleted. File removal runs through a durable cleanup queue after workers are fenced and drained. See [permanent deletion](permanent-deletion.md). Zotero originals are untouched.

The preference `extensions.zotero.knowledgemcp.treeExpansion` stores open row IDs and known library IDs as JSON through `Zotero.Prefs`, independently of Zotero's `sourceList.persist`. Disclosure toggles, native container closing and automatic ancestor expansion after selection/creation save the state immediately. Startup and addon reload restore the overview, default/other libraries and nested folders, including hidden descendants' expansion beneath a collapsed ancestor. An explicitly empty saved open set remains collapsed. Missing or invalid preference data uses the original first-run defaults. Unloading a window does not write an older snapshot over the last interaction. Trash has no expandable children.

## Drag-and-Drop Copies

Dragging top-level bibliographic items or standalone attachments from Zotero into a knowledge library/folder adds their metadata/membership through the same admission service as the context menu. Multiple selections are supported. Dropping on **My Knowledge Base** uses the default knowledge library. The knowledge items pane also accepts membership drops for its single selected library/folder.

Knowledge-to-knowledge membership copies retain the source. Knowledge-to-Zotero drops forward the original native item IDs to Zotero's collection-tree copy handler. Same-library items are added to the destination collection; cross-library copies and linked-item deduplication follow Zotero's own implementation and permissions. No knowledge membership is removed or changed by this native copy. Drops in a native collection's middle pane use its container copy path, avoiding attachment reparenting onto the item under the pointer.

Membership and outgoing native-item copies always retain their source, including when a modifier requests a move. An entirely duplicate copy selection has no valid drop target. A mixed selection adds only missing knowledge memberships; Zotero handles duplicate native collection memberships. Existing native-to-native drag behavior is delegated unchanged. Knowledge admission drops reject trash sources, deleted items, child items, notes/annotations as independent resources, external files/URLs and native collection-tree rearrangement payloads. Native Trash, Publications and saved searches are not destinations for a knowledge drag. Read-only native targets and linked-file/group restrictions continue to use native checks. Knowledge organization does not grant native write permissions.

The plugin's **Trash** accepts recoverable deletion drops on its left-tree row (orientation 0 only) and in its open middle pane. Item payloads must originate from an active knowledge overview/library/folder/combined scope and resolve to resources in that captured source scope. The move removes all placements in the source's knowledge libraries, preserving other libraries and unselected resources. Native Zotero sources, Trash sources and external payloads are refused. Source scope comes from the drag source rather than the current selection at drop time.

Knowledge folder drag-start serializes plugin folder IDs under `application/x-zotero-knowledge-folders`, separate from Zotero's native collection IDs. Only active folders are accepted. A drop calls the batch folder-delete service directly, preserving literature at the knowledge-library root and retaining restoration records in the dedicated Trash tables. Selected descendants covered by a selected ancestor are deleted once. All selected folders are validated and deleted in a single transaction; any failure rolls back the complete batch. Native copy targets and knowledge library/folder rearrangement refuse the folder payload. Drag end, successful drop and shutdown release the owned folder drag source; drop cleanup clears highlights/hover timers. The existing context-menu confirmation remains separate from explicit recoverable Trash drops.

`ui/knowledge/drag-drop.ts` owns reversible per-view adapters and hover cleanup. Shutdown cancels a pending expansion over a knowledge row, removes knowledge-only entries from native expansion tracking, and releases its adapters without removing a later plugin wrapper. No new schema, queue, parser or MCP capability is introduced.

An owned document-level capture listener releases folder drag state on `dragend`, including when virtualized rows retain callback references after addon replacement. Disposal removes this listener; it must not clear another drag's source.

## Native UI and Usage

1. In Zotero's item list, select a bibliographic item or standalone attachment and choose **Add to Knowledge Base**. The default target is **Default Knowledge Base** under the level-zero **My Knowledge Base** tree entry.
2. Choose **Add to Knowledge Base…** to select another knowledge library or nested folder. Use the collection-tree context menu to create a knowledge library/folder. These are independent plugin records, not Zotero collections.
3. Select a knowledge library to see all its admitted items, including items with and without folder placements, or an individual folder for its direct members. There is no separate Unfiled entry. The middle pane displays the original native items, with native quicksearch/tag filtering restricted to that view's admitted identities. Knowledge roots/libraries use the project's purple Book K logo.
4. A hollow circle before the native title text means **Added to knowledge base — not processed**; a filled circle means parsed and a half-filled circle means partially parsed. Native tooltips and accessible labels explain the state. A warning icon indicates metadata refresh failure. There is no added status column or modified title string.
5. **Knowledge Base Information** appears as a peer right-pane section and sidenav entry. It uses a two-column label/value layout like the native Info section, with separate status, location, metadata, source, version, updated, attachment, content and index fields. Attachments show their name and a secondary type/availability line. Refresh and source-navigation actions are grouped below the fields. Original metadata and attachment editing remain Zotero's responsibility.
6. Within a knowledge folder/library, use its corresponding remove action. Delete in a knowledge items view removes knowledge membership. Native creation/collection-edit paths remain guarded; item drags use the copy rules above.
7. A native Zotero collection offers **Add Collection Items to Knowledge Base…**. This adds its current direct items once to the selected knowledge location. It does not mirror the collection tree or subscribe to subsequent collection membership changes.
8. Right-click a knowledge library and choose **Delete Knowledge Library…** to remove its structure and optionally its exclusive knowledge items. Read the native confirmation checkbox before accepting; cancellation changes nothing.
9. Right-click a knowledge folder and choose **Delete Knowledge Folder…**. Its subfolders are removed together; their items remain in the knowledge library.

Creation reveals and selects the new library/folder automatically. Creating a child expands every ancestor needed to show it. Disclosure arrows, retained keyboard callbacks and native container closing share the same plugin expansion state; refreshes preserve that state. Tree rebuilding preserves all visible selected row identities, focus and the Shift-selection anchor, including native Zotero collection multi-selection. It does not emit redundant selection events, change event suppression or scroll the view. When some selected rows disappear, other selected rows remain selected and the item scope updates. When all selected descendants become hidden, collapse moves selection and item content to the collapsed folder; deleting all selected knowledge nodes falls back to the overview. Empty selections remain empty.

Ctrl-click toggles knowledge folders or library roots in the selection, Shift-click selects a visible range, and Ctrl+A selects visible siblings sharing a parent with a selected location. Multiple folders may belong to different knowledge libraries; the middle list shows their direct members as a deduplicated union. Multiple library roots show the union of those libraries' resources. Quicksearch/tags filter the combined scope; metadata refresh retains the selection and filters. Mixing library roots with folders or the overview, or mixing native and knowledge locations, retains Zotero's focused-row compatibility fallback.

The pane accessor exposes one cached plugin-owned union scope instead of passing unsupported multiple custom row types into ZoteroPane's selection guard. The physical collection-tree selection remains intact. This scope has no persistent record and never claims to be a native Zotero collection. Adding selected literature and copying items to an explicit destination continue to use existing actions. Creating a child, deleting a library/folder, removing item membership and incoming drops into the middle list require a single location; those ambiguous menu actions are hidden for multi-selection, and the explicit left-tree drop target remains available. Multi-folder drops to Trash use the batch folder-delete service described above; unrestricted mixed-location batch menu deletion is unavailable.

Names are trimmed and checked before insertion. Active/nondeleted knowledge-library names must be unique; folders must be unique among siblings in the same library (root folders included). The same folder name is allowed at another location. Duplicate creation produces a readable "already exists ... choose a different name" prompt and preserves existing records. Expected operation/validation failures use `KnowledgeUserError`; unexpected native/database exceptions are converted to a generic retry message in alerts, batch admission results and metadata-refresh warnings. SQL statements, bindings and database constraint messages are not shown to users.

UI text follows Zotero's interface language and supports English, Simplified Chinese, German, French, Spanish, Japanese and Traditional Chinese, with English fallback for other languages. See [localization and extension instructions](localization.md) for the Fluent resources and language checks. The native item-pane and menu registrations use supported Zotero plugin managers. Title-cell decoration and the independent tree use reversible instance adapters around internal APIs. These require revalidation after Zotero updates; they are not a stable public extension contract. See the [API feasibility assessment](knowledge-ui-feasibility.md).

## Implementation Boundaries

- Metadata admission, parsing/publication, collection synchronization, retrieval and MCP are separate implemented services. A metadata-only item has no fabricated extracted content.
- Canonical attachment availability and readable content are established by the processing/read services, not inferred from bibliography alone.
- An attachment admitted as a standalone resource cannot silently merge into a different parent resource. Reassociation requires an explicit workflow and current conflicts retain saved state.
- Multi-folder drops to Trash are supported and deduplicate selected parent/child subtrees. Mixed library/folder context actions still require an unambiguous destination; this is not unrestricted batch deletion of every location type.
- Separate-window, accessibility, scaling, theme and cross-platform manual acceptance remain bounded by [project status](project-status.md).

## Verification

Use the knowledge-library, collection-sync, drag/drop, Trash-scale and permanent-
deletion regression suites. Check duplicate admission, overlapping memberships,
unavailable native sources, transactional rollback, rename/move, recovery and
shared-file/reference preservation. Isolated native checks separately verify tree,
menu, item-pane, selection, temporary scopes and cleanup in affected locales.
